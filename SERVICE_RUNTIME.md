# Service runtime

Consumers select places and compare candidates by estimated terrain grade or provider travel time. There is no mobility-profile selector or cycling priority. `/api/action` accepts `search`, `journey`, `advance`, read-only `status`, and `cancel`. Job commands enforce ownership. `POST /api/entrance` independently inspects a selected roadside storefront and does not certify its approach route.

Configure runtime secrets using the names in `.env.example`. Local development can read process environment variables. Production reads the request-scoped worker environment supplied in `build/sites-worker.ts`. Private REST, inference and renderer keys are never embedded in client bundles or returned to browsers. GET /api/map-config returns only the browser-public Naver Maps Client ID independently of inference and routing credentials. The obsolete Kakao roadview configuration endpoint is removed. Local preview runs on localhost:3000 and the Cloudflare development plugin reads ignored .env.local secrets. Set NAVER_MAP_CLIENT_ID, enable Dynamic Map in Naver Cloud Maps, and register the actual web origin, including http://localhost:3000 for development. One SDK owner loads ncpKeyId with submodules=panorama; a Naver Client Secret is not needed. Retain KAKAO_REST_API_KEY for place search and walking/alternative routes. The current display and streetview path no longer reads KAKAO_JAVASCRIPT_KEY. After editing .env.local, restart the local app and reload the browser. Replace CHATKHU_API_KEY when changing inference credentials; change CHATKHU_MODEL only when changing the model. This does not change the inference gateway or request protocol.

The server selects Kakao routing when KAKAO_REST_API_KEY is configured; otherwise it requires TMAP_API_KEY. It never switches routing providers after an upstream error. Kakao's three real walking modes are requested and equivalent geometries deduplicated; a mode label is not a wheelchair-accessibility guarantee. Display and default streetview use native Naver Maps SDK functionality, without Kakao display/capture fallback. The private renderer captures the application-owned Panorama page directly, not a second consumer-map navigation. Search coordinates and route geometries remain [longitude,latitude]; conversion to native latitude/longitude objects occurs at the display boundary. Panorama sources retain the actual opaque pano ID, location, canonical positive-down tilt, normalized heading and actual FOV. Requested zoom 0/1/2 selects deliberate 90/60/40-degree framing presets, not native Naver zoom. The embedded viewer reconstructs the actual saved pose by pano ID and never substitutes a nearby coordinate lookup. Historical Kakao captures remain archived images plus external original links. ChatKHU remains independently configured. Production renderer URLs require HTTPS and bearer authentication; local development may use the included localhost renderer. It receives `POST {coord:[longitude,latitude],heading:number,target?:[longitude,latitude],tilt?:number,zoom?:0|1|2,maxDistance?:20|60}` and returns JSON null only when the successful lookup is outside the permitted camera distance, or an image/source object. Authentication, configuration, lookup and painting failures are service errors, not physical barriers or proof of absent coverage.

The optional `google` imagery selection uses the server-only `GOOGLE_STREET_VIEW_API_KEY` and Street View Static API. The Naver display map and walking-route provider remain unchanged by this imagery selection. Missing credentials stop analysis with a configuration notice; Google mode never falls back to another imagery provider. Google imposes restrictions on image storage, derived content and use alongside non-Google maps; an operator must establish applicable permissions before using this research integration.

`services/roadview-renderer/` contains the real Playwright capture service. Provider terms and production hosting remain operator responsibilities. Responses are size-limited and parsed before use; original viewer links are restricted to supported providers. Exact captured bytes are persisted **before** the model call in private, multipart D1 storage, separate from the job JSON. Status polling exposes only capture metadata and same-origin `/api/journey-image?id=...` URLs. That endpoint enforces job ownership and 30-minute expiry, returns the original bytes with `private, no-store`, and cannot proxy arbitrary URLs. Expired-job cleanup cascades to image metadata and parts.

Durable version-8 jobs use revision/lease fencing so cancellation or a replaced lease prevents late state and image writes. A client submits one `advance` at a time and polls read-only `status` while it waits. Route captures use D1 and expire with the job. Entrance captures use a private no-store response and client-memory Blob URLs, with no D1 or localStorage persistence.

A recommendation requires observations for every required sample, with no blocked or unknown result. Otherwise the response is `limited` and the map shows candidates without a recommendation badge. This is an observation-based comparison, not a guarantee about continuous unpictured space. Older images are not excluded merely because of their age; capture dates are shown and do not establish current conditions. Location and direction must match the requested observation. Numeric terrain grade is not inferred from image pixels.

Every provider candidate, including accepted detours, receives an SRTM30m terrain profile where available. Grades use at least 60m of actual path length, preserve null gaps, and use a direction-independent physical partition. The UI shows signed estimates and lets users compare gentler terrain versus travel time without overriding obstacle exclusions. Terrain grade is not a measured sidewalk or ramp grade and cannot certify passability. Map emphasis thresholds are display preferences, not safety limits.
Selected-crossing alternatives accept bounded provider/map centreline differences only with meaningful directional traversal, bidirectional trace coverage and no competing crossing ambiguity. Provider approaches are also checked against directed map barriers; denied-access ways remain represented as blocked edges rather than disappearing from validation. Neither map barriers nor missing imagery are labelled as image-observed obstacles.

Entrance results retain visible approach stairs even when the remaining connection is obscured. A separate “stairs visible in the photo” headline can describe the photo while the selected branch and full entrance verdict remain unknown. Photo-viewpoint suggestions are not physical travel directions.



The server requests real waypoint detours around shared physical obstacles and separately around unresolved mandatory connections; candidates must remain connected, distinct and outside the excluded passage. It can still finish without an acceptable alternative. Details distinguish provider instructions from direct image observations, position the problem, and report searching, finished or interrupted exploration with request/candidate counts. Missing data and service failures do not become physical barriers. Precise sidewalk geometry, measured curb heights/grades and wheelchair-user field validation are not established. The navigation panel presents route steps; it does not track live position or reroute on deviation.
